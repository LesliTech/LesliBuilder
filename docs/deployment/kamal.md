# Deploying with Kamal

LesliBuilder uses the Kamal version declared by the host application's
`Gemfile` and locked in `Gemfile.lock`. Always run deployment commands through
the local binstub:

```shell
bin/kamal deploy
bin/kamal deploy -d demo
bin/kamal deploy -d production
```

Do not rely on a globally installed `kamal` executable. Using `bin/kamal`
keeps local development, CI, and deployments on the same Kamal version.

## Local deployment environment

Create the workstation-local environment file from the committed example:

```shell
cp .env.kamal.example .env.kamal
```

Add the 1Password account, item, and secret references required by the host
application. `.env.kamal` is ignored by Git; keep shared variable names and
setup guidance in `.env.kamal.example`.

The `bin/kamal` wrapper loads `.env.kamal` before starting Kamal. Variables
already present in the process environment take precedence, which allows CI or
another deployment environment to provide the same values without creating
the file.

Because the variables are already available to Kamal, `.kamal/secrets` can use
them directly when fetching credentials. Its nested secret commands also use
`bin/kamal`, ensuring they run the version locked by the host application.

## Host application requirements

Every host application that deploys Lesli with this convention must:

1. Declare `gem "kamal", require: false` in its `Gemfile`.
2. Commit the resulting `Gemfile.lock` and `bin/kamal`.
3. Keep `.env.kamal` ignored and commit an `.env.kamal.example` containing only
   variable names and safe documentation.
4. Run Kamal commands as `bin/kamal ...` from the host application's root.

If the binstub is regenerated by Bundler, preserve the `.env.kamal` loading in
`bin/kamal`; a default generated binstub does not load that file.
